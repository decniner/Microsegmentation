01 · WHY

Why microsegmentation?

Traditional network security often assumes that once something is inside the network, it can communicate with many other things. Microsegmentation challenges that assumption.

In plain language

Most corporate networks are built for connectivity. A user PC can reach a server, the server can reach a database, and the database can reach backup, monitoring, DNS and authentication services. That is convenient — and it is also why one compromised workload can often reach many others.

Microsegmentation narrows communication down to what is actually required. Not "inside versus outside". Not "which VLAN". It asks a much more specific question:

Which workload is allowed to talk to which other workload, over which service, and why?

Core message: Microsegmentation is not simply creating more network segments. It is controlling which workloads are allowed to communicate with which other workloads, and why.

“The surprise” — why blind rule-writing is dangerous

The application appears to work normally. Then dependency mapping reveals that it also communicates with an unexpected legacy service that nobody documented.

UNDOCUMENTED DEPENDENCY: Trading Application → Legacy Batch Service

If a team had written firewall rules from documentation alone, this flow would have been blocked during enforcement — potentially breaking a nightly batch process at an inconvenient hour.

The lesson: dependency discovery comes before enforcement. Observed traffic is evidence; documentation is a hypothesis.

Business context — why technical classification is not enough

Technically…

A database is just a database. It stores rows, answers queries, runs backups.

But in business terms…

That same database may support a critical trading application with regulatory reporting obligations and a recovery time objective measured in minutes.

Policy design should therefore consider

Business criticality
What happens if this stops?
Data sensitivity
What data does it hold or touch?
Regulatory requirements
What must be evidenced?
Application dependencies
What breaks if this is isolated?
Operational importance
Is it needed to run the estate?
Exposure

Ownership
Who approves change?

Exception workflow

Enterprises will encounter cases where a standard policy cannot immediately be applied. Exceptions must be governed.

REQUEST↓ BUSINESS JUSTIFICATION↓ SECURITY REVIEW↓ RISK REVIEW↓ APPROVAL↓ TIME-LIMITED EXCEPTION↓ REVIEW↓ REMOVE OR RENEW

Exceptions should not quietly become permanent architecture. Every exception needs an expiry date, an owner and a review.

Where microsegmentation fits in Zero Trust

Microsegmentation can support Zero Trust, but microsegmentation is not the same thing as Zero Trust.

  • Identity — who or what is acting.
  • Device trust — is the device known and healthy.
  • Authentication — proving the claim.
  • Authorization — what that identity may do.
  • Least privilege — only what is required.
  • Continuous verification — trust is re-evaluated, not granted once.
  • Microsegmentation — limiting which workloads can reach which.

Traditional network segmentation often operates at larger boundaries. Microsegmentation can apply more granular workload-level policies.

Microsegmentation vs. firewall

Microsegmentation does not necessarily mean replacing firewalls. It adds a more granular layer inside a defence-in-depth model.

The SRE / operations perspective

A technically perfect security policy that breaks production is not a successful implementation.

Operational requirements

  • Availability
  • Change management
  • Monitoring
  • Rollback
  • Dependency discovery
  • Incident response
  • Automation
  • Documentation

Why it matters

Security controls that are not operable will be worked around. If a policy blocks a legitimate flow at 02:00 and nobody can restore service, the organisation will not trust the programme — and the exception list will grow until it becomes the architecture.

Security and reliability must be designed together.

What can go wrong?

Technical risks

  • Unknown dependencies
  • Legacy systems
  • Incorrect policies
  • Tool failures
  • Visibility gaps
  • Policy drift

Operational risks

  • Application outages
  • Change collisions
  • Emergency access problems
  • Poor ownership
  • Excessive manual work

Organisational & program risks

  • Security vs. operations conflict
  • Unclear accountability
  • Lack of application-owner participation
  • Exception sprawl
  • Automating before understanding
  • Measuring deployment instead of risk reduction
  • Treating microsegmentation as a one-time project

The ideal process

Final takeaway

Microsegmentation is not a firewall rule-writing exercise.

It is an ongoing process of understanding workloads, understanding dependencies, defining legitimate communication, enforcing least-privilege connectivity, monitoring behaviour, and continuously adapting policies as the environment changes.

The technology matters. But the operating model matters just as much.
